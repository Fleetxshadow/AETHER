## 1. Architectural Principles & Boundaries

1. **Zero UI Disruption:** Frontend visual components, layouts, typography, styling, and 3D scenes in AETHER must remain visually identical. Integration occurs strictly through data providers, typed hooks, and server-side API routes.
2. **Absolute Data Provenance:** Every piece of telemetry, observation, and inference result must carry an unambiguous data source state:
   - `LIVE`: Generated by authentic physical sensors or verified real-time neural network inference runtimes.
   - `DEMO`: Static synthetic demonstration records used for offline display, replay, or testing.
   - `STALE`: Previously live data that has exceeded its valid time-to-live ($T > 60$ seconds) without an update.
   - `OFFLINE`: Sensor, camera, or model runtime is disconnected or unreachable.
   - **Crucial Rule:** Synthetic demo data must NEVER be commingled with `LIVE` measurements to manufacture false incidents.
3. **Simulation-Only Boundaries:**
   - **MAVERICK:** Strictly a simulation-only autonomous navigation engine on 2D/3D digital twin grids. No physical motor or drone actuator commands shall ever be emitted.
   - **CORE:** Strictly generates **guarded recommendations** for human operator review. Autonomous emergency dispatch without operator confirmation is prohibited.
4. **Fail-Closed Safety:** If any telemetry input is malformed, out of physical bounds, or missing, the CORE safety supervisor defaults to `emergency_land_sim` or `hold_position`.
5. **No Cloud Compute Costs:** All inference and verification execute on the local machine (Intel Core i5-1235U, CPU runtime). Cloud GPU provisioning (e.g., RunPod) is strictly prohibited without explicit pre-authorization ($0.00 compute spend).

## 3. Standard Data Schemas

### 3.1 Error Envelope Schema
Every endpoint that fails returns HTTP 4xx or 5xx with this structure:
```json
{
  "error": "Descriptive human-readable error message",
  "code": "NEXUS_ERR_CODE",
  "details": {},
  "timestamp": "2026-10-27T04:30:00.000Z",
  "source": "OFFLINE"
}
```

### 3.2 Channel Types and Physical Units
All telemetry measurements must match these channel keys and exact units:
| Channel | Type | Bounds | Allowed Unit |
|---|---|---|---|
| `temperature` | float | `[-100.0, 2000.0]` | `°C` |
| `speed` | float | `[0.0, 350.0]` | `km/h` |
| `rainfall` | float | `[0.0, 5000.0]` | `mm` |

| `altitude` | float | `[0.0, 50000.0]` | `m` |
| `battery` | float | `[0.0, 100.0]` | `%` |

## 5. Codex Hardware Boundary

1. Codex manages low-level firmware for ESP32 and Raspberry Pi.
2. Hardware posts telemetry to NEXUS server via `POST /api/hardware/telemetry` or serial pipe.
3. If hardware disconnects, status becomes `offline` and AETHER transitions to labeled `DEMO` fallback without throwing unhandled exceptions.
